# Auto Delete Session (ADS) 2.1.0

[![Ask DeepWiki](https://deepwiki.com/badge.svg)](https://deepwiki.com/znq19/KiraAI_auto_delete_session_plugin)

> KiraAI 智能会话管理插件 — 自动检测上下文溢出，压缩旧对话、重开轻量会话，让你的 bot 长时间聊天也不"失忆"、不卡顿。

**一句话说明**：当你和 bot 聊得太多、上下文快撑爆时，ADS 会在后台帮你把早期聊天内容"压缩成笔记"写回会话开头，然后清掉冗长的原始记录。bot 继续聊时有"笔记"可看，但不用拖着一大坨旧消息——省 token，保速度，不断片。

---

## 先跑起来

1. 把整个 `KiraAI_auto_delete_session_plugin-main` 文件夹放进 KiraAI 的 `data/plugins/` 目录。
2. 重启 KiraAI，进入 WebUI → 插件管理，确认 **Auto Delete Session** 已启用。
3. 默认配置就能用。打开「重开前自动摘要」区，把摘要模式设为 `sync`（同步生成）或 `async`（后台生成），然后正常聊天即可。

> 不想生成摘要？摘要模式选 `off`，插件只会在超限时清旧消息、保留最近 N 轮——轻量干净。

## 核心功能

### 自动检测，超了就"压缩重开"

两种检测维度，可组合使用：

| 模式 | 怎么判断 | 适合谁 |
|------|----------|--------|
| **Token 检测** | 估算当前会话 token 数，超过上限就触发 | 关心 API 费用、怕超模型上下文窗口 |
| **轮数检测** | 会话轮数达到框架窗口上限就触发 | 和框架原生窗口对齐，简单粗暴 |
| **任意触发** | token 或轮数任一先到 | 最保险的兜底方案 |

### 重开前自动摘要（三种模式）

被清理的旧聊天不会直接扔掉——可以先用 LLM 压缩成一段摘要，注入新会话。

| 模式 | 效果 | 延迟 |
|------|------|------|
| `off` | 不生成摘要，只清理 | 无 |
| `sync` | 重开前生成摘要并写入，第一轮就能看到 | 偶尔阻塞几秒 |
| `async` | 先重开，摘要后台生成后补写 | 第一轮看不到，第二轮起生效 |

### 累积摘要 — 越聊越持久

常规摘要每次都是"重新看一遍被删的消息→生成新摘要"。ADS 则：它会拿**上次的旧摘要** + **这次新增被删部分**，让 LLM 合并成一版更凝练的累积摘要。

- 历史信息层层叠加，不丢失
- 累计超长时自动再压缩（self-compress）
- 摘要固定在记忆头部，位置恒定，前缀缓存友好
- 必须指出：受限于独立的LLM当前能力，摘要的**细节磨损和失真**是必然存在的，甚至会有很多一眼错的内容。可尝试**自行修改各摘要提示词，包括写上部分或完整人设（但这样会增加token消耗）**

### 预热压缩 — 零阻塞体验

开了 sync 模式但嫌每次重开要等几秒？开启**预热**：在 token/轮数到达阈值 70%（可调）时，后台就开始偷偷压缩。等真正触发重开时，摘要已经准备好了——收割即用，几乎不阻塞。

### 写穿式覆写 — 保留会话元信息

传统做法：删掉旧会话 → 建新会话。问题是标题、描述这些元信息全丢了，切回聊天列表看到一堆"未命名"。

ADS v2.x 默认**写穿覆写**：直接 `write_memory` 覆盖会话记忆，标题、描述纹丝不动。

### 时间队尾化 — 修复前缀缓存

KiraAI 的 system prompt 里通常带时间戳，每分钟变一次，导致整个 system prompt 前缀缓存报废。

开启此功能后，时间信息被移到 user prompt 末尾（非持久化），system prompt 跨分钟保持稳定，前缀缓存完整命中。

### 手动命令 `/resum`

随时输入 `/resum`（可自定义），手动触发一次压缩重开。支持权限白名单、自定义成功/失败文案。

## 和 ContextCondensation（CCS）有什么不同？

这两个插件目标相似——都是帮 KiraAI 管理超长上下文——CCS的路是"以量换质"，ADS是"极限再说"。各有各的适用场景。

| 维度 | ADS（本插件） | CCS |
|------|--------------|-----|
| **思路** | 检测到超限 → 压缩被删部分为摘要 → 清空旧消息、保留最近 N 轮 | 持续分层压缩，摘要逐步替换原始轮次 |
| **信息保留** | 旧对话被清理，摘要 + 最近 N 轮原文保留 | 所有轮次逐渐被摘要替代，越老越浓缩 |
| **前缀缓存** | 摘要固定在头部 + 时间队尾化，命中率很高 | 摘要块位置固定，写入后周期内稳定 |
| **摘要策略** | 一次性压缩被删部分 + 累积合并（旧摘要 + 新增量） | 分层渐进：原始 → 分组摘要 → 合并摘要 → 最终摘要 |
| **后台压缩** | 预热模式：阈值 70% 时预生成，触发时收割即用 | 每有新轮次即启动后台管道，持续压缩 |
| **触发方式** | 模板式：token/轮数超阈值一次性触发，并可双重检测 | 注入式：每轮检测，达到窗口上限注入摘要 |
| **LLM 调用** | 较少。只在触发时调（预热可提前 + 累积复用可减） | 较多。每轮后台持续压缩，每层分组都需要调用 |
| **适合场景** | 日常聊天、长对话但不想折腾细节的用户 | 对上下文保真度要求极高、愿意用资源换质量的用户 |

**简单总结**：

- **想要省心？用 ADS。** 超了清掉，留份摘要，聊得轻快但可能细节失真。
- **想要极致保真？用 CCS。** 分层压缩保留更多细节，但可能通常会更多 LLM 调用。
- 而且，ADS通过让触发重开压缩时**合并摘要可后台生成，先用已生成的摘要直接拼接，等生成好了再替换回来**的方式，虽然降低一次回复质量和可能的命中缓存，但解决了CCS也可能存在的唯一一次回复堵塞。 

两者可以互相替代，但**不要同时启用**。ADS 默认会自动禁用 CCS（可在兼容设置里调整）。

> 关于 CCS 的完整设计思想，强烈推荐阅读 [DESIGN.md（CCS 设计文档）](https://github.com/OldTangyuan/KiraAI-ContextCondensation)——对分层压缩和 KV-cache 友好架构讲得非常透彻。

## 配置速览

WebUI 里的配置分成六个区，常见的改这几个就行：

| 你想做什么 | 改什么 |
|-----------|--------|
| 不要频繁重开 | 调高 `max_tokens` 或 `trigger_rounds` |
| 重开后上下文太短 | 调大 `keep_recent_turns` |
| 重开时想保留更多信息 | 摘要模式选 `sync`，摘要提示词输出上限写到 800-1000字并同步改大其他配置项 |
| 不想摘要生成时堵塞回复 | 开启 `preheat_summary`（预热），比例设 0.7 |
| 想手动控制何时重开 | 开启压缩重开命令 `/resum` |
| 想看到摘要到底写了什么 | 打开 `enable_summary_logging` |

其余高级选项保持默认即可，99% 的场景不用动。

## 常见问题

**Q: 和 CCS 一起开会怎样？**

A: 两个插件都会覆写会话记忆，同时开会互相覆盖、摘要乱套。ADS 默认检测到 CCS 时自动禁用它。如果非要用两个——不建议。

**Q: 摘要会不会胡说八道？**

A: 摘要是用 LLM 生成的，质量取决于你选的摘要模型。建议用快速便宜但又兼顾智力的模型做摘要，或者在 prompt 里强调"只提取事实，不要编造"（但并非总是有用，图一乐，也期待大火的研究）。

**Q: 压缩重开后命中缓存会清空吗？**

A: 这正是 ADS 做了很多工作的领域：摘要固定在记忆头部位置恒定 + 时间队尾化修复前缀缓存。sync 模式下重开后第一轮通常就能较完整命中缓存。

**Q: 为什么 token 估算和实际有差距？**

A: ADS 按 `字符数 / chars_per_token` 估算，中文默认 2.0（一个汉字约 2 token）。如果模型的分词器不同，实际 token 数会有偏差。可以微调 `chars_per_token` 参数（中文建议 1.5-2.5）。
